===== frontend
The frontend (about 3.8k lines of non-test TS/TSX in web/src) treats the server as one watcher with one browser. A single `State` document (web/src/lib/schema.ts:100-115) carries global fields: `enabled`, `interval_seconds`, `next_check_at`, `max_trips`, `checkout_url` (one VNC link), `login_configured` (BCF_USER/BCF_PASS env), `alerts_configured` (Pushover env) and `watcher` (one heartbeat). It has no user identity. The server builds one snapshot and sends it to every WebSocket client (src/ferry_watch/server.py:142-153), so per-user filtering has to happen in the operator; the UI cannot do it. Six areas are shaped around one loop and must move to per-trip or per-user data: the global VNC link (App.tsx:72 → TripCard → CartBanner.tsx:136-140, WatcherCard.tsx:222-226), the global pause switch (Header.tsx:61-86), the interval picker and next-check countdown ring (WatcherCard.tsx:107-130,186-197, lib/watcher.ts:19-32), the stalled-watcher banner (App.tsx:34-36, Banners.tsx:119-125), the auto-cart gating (TripSheet.tsx:317,470-500) and the trip quota (App.tsx:28,58). Each trip already has a `session.logged_in` field (schema.ts:86), which fits a per-pod login model. Two things in the target design matter more than the UI code. First, a BC Ferries credential form in the operator-served dashboard would defeat the isolation goal, because the operator serves that page's JavaScript. Second, the VNC viewer today is served on the same origin as the dashboard (Dockerfile:36-38), and per-tenant pods must not be. New UI needed: a browser-pod lifecycle badge and status per trip, an "Open this trip's browser" link per trip, a "log in inside your browser" call to action, a who-am-I/user menu, a settings sheet for the Pushover user key, an admin page with tenants and capacity, and hash routes for the admin page and alert deep links. Overall frontend size is L: roughly 1.5-2.5k changed or added lines including tests. The biggest pieces are the WatcherCard replacement, the new AdminPage, and changes to the schema, the trip-status helper and the test fixtures, which every test uses.

## One global State document with no identity; the server sends the same snapshot to everyone
StateSchema (schema.ts:100-115) and its server counterpart state_view (views.py:121-143) mix global and per-trip data. Global: enabled, interval_seconds, next_check_at, max_trips, trip_defaults, events, checkout_url, login_configured, alerts_configured, watcher. Nothing identifies the viewer. Hub._payload builds one JSON payload and offers it to every client (server.py:142-153, 162-165). The UI has a single entry point for live data, /api/ws (live.ts:42-46), plus GET /api/state (api.ts:182), and caches one State under STATE_KEY (state.ts:10). For multi-tenancy the operator must build a separate payload per user, and the UI needs a `me` block. Proposed additions: MeSchema {id, name, email, is_admin, paused, max_trips, alerts_configured, pushover_key_hint}, plus control_plane {healthy, heartbeat_at} and capacity {can_add, reason} on State. Global checkout_url, login_configured, alerts_configured and max_trips get removed or moved under `me`. Size: schema.ts M.

## Strict zod enums mean a new server value breaks the whole dashboard
StateSchema drops unknown keys (schema.ts:1-5), but enum values are strict (Sailing.status at schema.ts:58, Cart.status at :66, ActivityEvent.kind at :94). If the server adds a new event kind or browser phase before the frontend knows it, request() throws a 'schema' ApiError (api.ts:125-131) and the whole page shows 'Unexpected data' (Banners.tsx:102-104). WebSocket messages are dropped with a console warning (live.ts:126-130). Kubernetes-derived phases and reasons change over time. Use z.enum([...,'unknown']).catch('unknown') for browser.phase and reason, and either deploy the frontend first or give ActivityEvent.kind a fallback. The ActivityCard KIND map (ActivityCard.tsx:8-13) needs an entry for any new kind such as 'browser'.

## The boot_id/seq merge rule assumes one server process
supersedes() accepts any snapshot with a different boot_id as newer (state.ts:25-27). mergeSnapshot uses it for WebSocket pushes, polls and mutation responses (state.ts:30-33, 40-50). If the operator API runs more than one replica behind a Service, a WebSocket on replica A and polls or mutations on replica B would flip the cache back and forth on every message. The two options are a single API replica (leader-elected) or a globally monotonic per-user revision (for example from the store), with the boot_id comparison dropped. Size: state.ts S if one replica, M otherwise.
refs: web/src/lib/state.ts:25-33, web/src/lib/state.ts:40-50, web/src/lib/state.test.ts:7-66

## Today's VNC viewer shares the dashboard origin; per-tenant pods must not
The Dockerfile serves KasmVNC's viewer under /vnc 'so it shares a hostname with the app' (Dockerfile:36-38). Xvnc runs with no authentication (-DisableBasicAuth -SecurityTypes None, entrypoint.sh:20-25) and relies on the proxy plus a NetworkPolicy (entrypoint.sh:4-7). The dashboard API accepts any same-origin request as trusted (server.py:193-198), and its CSP is connect-src 'self', default-src 'self', frame-ancestors 'none' (server.py:240-249). If tenant pods serve their viewer HTML/JS under a path on the dashboard origin, a compromised pod can run script as the dashboard origin, read the viewer's /api/state and change their trips. Each pod's VNC needs a separate origin (for example a per-pod subdomain), and the dashboard should open it in a new tab: today's CSP blocks cross-origin iframes, and a new tab works better on phones.
refs: Dockerfile:36-38, entrypoint.sh:4-7, entrypoint.sh:20-25, src/ferry_watch/server.py:193-198, src/ferry_watch/server.py:240-249

## Collecting BC Ferries credentials in the dashboard would defeat the isolation goal
The operator serves the dashboard's HTML and JS (server.py:466-477). Any credential field in that page is controlled by the operator, and so are any client-side encryption keys it relays, so a compromised operator could change the page to capture the password. The only intake that keeps credentials out of the operator is 'Log in to BC Ferries inside your browser'. StatusPanel shows a needs_login call to action that opens the pod's VNC; the user types the password into the pod's Chromium; the pod reports logged_in back, which reuses the existing trip.session.logged_in field (schema.ts:86). For this to hold, the VNC WebSocket must go from ingress directly to the pod, not through the operator pod, or keystrokes and screen contents pass through the operator. The Pushover user key is not a BC Ferries secret, and the operator needs it to send alerts, so it can be collected in a dashboard SettingsSheet. Make it write-only: the server returns only a hint such as the last 4 characters, and the form validates 30 alphanumeric characters.

App.tsx renders one dashboard view (App.tsx:16-105). package.json has no router dependency. IMPLICATIONS:
- The operator API must build a separate State per authenticated user, for both GET /api/state and each WebSocket client. Today's Hub builds one payload for all clients (server.py:142-153). The frontend cannot filter, because anything sent to it is readable.
- Each Trip in the API needs a `browser` block derived from pod status: phase (pending/starting/ready/crashlooping/evicted/stopping/stopped, with 'unknown' as a fallback), the Kubernetes reason, restarts, since, heartbeat_at from the pod's report, logged_in, and vnc_url. vnc_url is emitted only to the owner and only when the pod is ready.
- Per-pod VNC must be served from a distinct origin (for example a per-pod subdomain on a wildcard Ingress) and protected by Authelia forward-auth that checks the trip owner. It must not be a path under the dashboard hostname as Dockerfile:36-38 does today, and its traffic must not be proxied through the operator pod, or the operator sees keystrokes and the screen.
- Do not add a BC Ferries username/password form to the operator-served dashboard. Use a 'log in inside your browser' flow: StatusPanel shows a needs_login call to action, the user opens the pod's VNC, and the pod reports logged_in back. The Pushover user key form can live in the dashboard as a write-only field.
- Per-trip next_check_at (and interval_seconds if configurable) replaces the global loop timing. POST /api/check becomes POST /api/trips/{id}/check. Add POST /api/trips/{id}/browser/restart for crashlooping pods. PATCH /api/settings {enabled} becomes a per-user pause (and optionally an admin-only global switch). POST /api/alerts/test becomes per-user with a per-user rate limit.
- Adding a trip now starts a pod. The API should report capacity (State.capacity {can_add, reason}) and the per-user quota (me.max_trips). Decide whether an add over capacity is rejected (409/503 with an error the TripSheet can show) or accepted and left Pending.
- Run one API replica (leader-elected), or replace boot_id/seq with a globally monotonic per-user revision. Otherwise state.ts:25-33 makes the UI flip between replicas.
- Hash routes avoid backend SPA routing changes: #/ (my trips), #/settings, #/admin, #/trips/{id}. Pushover cart alerts should link to #/trips/{id} so the page can say whether the pod or cart survived before opening VNC. Otherwise the operator needs a catch-all route serving index.html.
- Admin data should come from a separate endpoint (for example GET /api/admin/overview) with its own zod schema: tenants (user, trips, pods by phase, last seen, alerts configured), capacity (nodes with allocatable CPU and memory, browsers running/pending/max), and a pod table (trip, owner, phase, reason, node, restarts, age). Actions: restart, delete, set quota. Keep it out of the per-user State.
- Rollout order: ship a frontend that tolerates new enum values (browser phases, event kinds) via .catch('unknown') before the operator emits them. Otherwise one unknown value fails parsing of the whole State (api.ts:125-131).
- Frontend size estimates. Schemas and lib: schema.ts M, api.ts S, state.ts S (M if multi-replica), live.ts S/none, watcher.ts M (becomes per-trip), trip.ts M. Existing components: App.tsx M, Header.tsx M, TripCard.tsx M, CartBanner.tsx S, StatusPanel.tsx M, WatcherCard.tsx L (replace with an Account card plus per-trip chips), Banners.tsx S, TripSheet.tsx S-M, ActivityCard.tsx S, RemoveTripDialog/removeConsequence S. New: BrowserBadge S, UserMenu S, SettingsSheet M, AdminPage L, hash router and deep-link page S-M. Tests: fixtures M, WatcherCard.test L, watcher.test M, trip.test M, StatusPanel.test M, App.test M, others S; new-component tests M-L. docs/api.md M. Total roughly L: about 1.5-2.5k lines changed or added against about 3.8k lines of existing source.

RISKS:
- Credential leakage by design: any BC Ferries credential field in the operator-served dashboard, even with client-side encryption, can be captured by a compromised operator, because the operator serves the page's JS (server.py:466-477).
- Same-origin VNC: if pod VNC pages are served under the dashboard hostname, as today (Dockerfile:36-38), a compromised tenant pod can run script as the dashboard origin. The same-origin check (server.py:193-198) would let it act as whoever opens the page.
- If VNC traffic is proxied through the operator pod, the operator sees typed passwords and the logged-in screens, which breaks the 'no secrets reach the operator' requirement even without cookie access.
- With one pod per trip, a user with N trips logs in N times. Whether BC Ferries tolerates one account logged in from several browsers at once, or ends older sessions (dropping held carts), is unverified and should be tested before committing to per-trip login.
- Eviction or OOM loses an in-memory cart. A Pushover link straight to a VNC URL would then open a fresh, logged-out browser with no explanation; the UI needs an 'evicted, cart lost' state.
- Adding a trip goes from instant to tens of seconds (scheduling, Chromium/KasmVNC image pull, startup). Without lifecycle states in the UI, users will see 'Waiting for the first check' for a long time and won't know why.
- Strict zod enums (schema.ts:58,66,94): if a new browser phase or event kind ships server-first, the whole dashboard breaks with 'Unexpected data from the server'.
- If several API replicas run, the boot_id/seq rule (state.ts:25-27) makes the UI jump between replicas' views.
- An admin view that can open tenants' VNC sessions or see their trip details would quietly reintroduce the cross-tenant access the design is meant to remove.
- WatcherCard and watcher.ts are the most heavily tested single-loop code (5 + 7 tests). Replacing them is the largest frontend rewrite and easy to underestimate.

OPEN_QUESTIONS:
- Is login inside the browser over VNC the only BC Ferries credential intake, or do you want automated re-login? Automated re-login needs credentials stored where the pod, but not the operator, can read them, which is hard to guarantee if the operator has RBAC on Secrets or pods/exec in tenant namespaces.
- Should a pod's BC Ferries login and profile survive pod restarts (a PVC per trip or per user), or is re-login after every restart or eviction acceptable?
- Pod granularity: one browser per trip (as stated) or one per user? Per-trip means N logins and N VNC links per user and more Chromium memory. Per-user gives one login and one VNC link with isolation still per tenant.
- What replaces the global 'Watching' switch: a per-user 'pause all my trips', an admin-only global kill switch, both, or nothing?
- Who controls the check interval: per trip, per user, or fixed by the admin with a minimum? This decides whether the interval picker survives and where.
- How does a VNC link work: a per-pod subdomain or a stable per-trip hostname, and how is it authorized (Authelia rule keyed to the owner vs a short-lived token minted by the operator, which could also mint one for itself)?
