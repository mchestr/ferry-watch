===== packaging-ci
Today one Dockerfile builds one image: a Playwright/Ubuntu-noble base with KasmVNC, matchbox and tini, the uv-installed `ferry-watch` wheel and the React build. CI has four jobs (Python lint/type/unit, browser contract tests in the same Playwright container, frontend, image), and the image job builds, smoke-tests and pushes to GHCR only on push to main or a v* tag. Despite the brief saying "multi-arch as today", CI builds and pushes linux/amd64 only. The Dockerfile already carries arm64 KasmVNC checksums, so arm64 is supported but never built or tested. The main blocker for an operator image without Chromium is the import graph: Playwright is a hard dependency and is imported at module level by bcferries/site.py. server.py, settings.py, views.py and watcher.py all import from site.py, and tests/conftest.py monkeypatches those modules, so every unit test and every entry point loads Playwright today. Splitting into an operator image and a browser-agent image needs a small refactor first: move Credentials, USER_AGENT, BASE_URL and search_url out of site.py. After that, a uv workspace with core, operator and agent members sharing one uv.lock, and a multi-target Dockerfile (operator, agent, plus a "standalone" target that is today's image). Several existing details bear directly on the goal that the operator cannot get tenant secrets. The login fills credentials into whatever `{base_url}/login` loads, with no origin check, and the base URL is already a parameter. KasmVNC runs with no auth and AlwaysShared. Chromium runs with Playwright's default --no-sandbox. Browser contexts are ephemeral, so restarting an agent pod drops its login and cart. In a cluster, an operator allowed to create pods can mount any Secret unless admission pins the pod spec. So the manifests (RBAC, a ValidatingAdmissionPolicy, NetworkPolicies) belong in this repo, versioned with the code, and they need tests against a real API server (envtest or kind/k3d), not just kubeconform. Personal mode can stay unchanged as a `standalone` build target that keeps the `ferry-watch` script, image name and existing smoke test.

## What CI runs today (4 jobs, image gated on all tests)
Triggers: push to main, v* tags, pull_request, workflow_dispatch. Concurrency cancels in-progress runs only for PRs. Job `python`: uv sync --locked, ruff format --check, ruff check, mypy (strict), then pytest -m "not browser" with coverage, then the Playwright version-match check. Job `browser`: pytest -m browser inside the pinned mcr Playwright container. Job `web`: npm ci, lint, format:check, typecheck, vitest, build. Job `image` (needs all three): buildx builds linux/amd64 with load:true, smoke-tests, then on push events only logs in to GHCR and runs a second build-push with metadata tags (semver, branch, pr, sha, latest on default branch). The GHA build cache is written only on push events. Only the image job gets packages:write.

## CI builds amd64 only, so arm64 is not "as today"
Both build-push steps set `platforms: linux/amd64`. The Dockerfile does handle arm64: a TARGETARCH case with a KasmVNC arm64 sha256, and uv.lock has the playwright aarch64 wheel. But no arm64 image is built, smoke-tested or published. Going multi-arch is new work, not a carry-over. The repo is public (checked with gh api), so native `ubuntu-24.04-arm` runners are an option instead of QEMU.

## Smoke test coverage and gaps
The smoke test runs `docker run -d -p 8765 -p 6080` and polls /healthz for up to 60s. It then checks that / contains <div id="root">, that /api/state has trips == [], and that /vnc/vnc.html is served. It does not use --read-only, --tmpfs, --cap-drop ALL, --security-opt no-new-privileges or a numeric --user, so README's claim that the image runs read-only and non-root is never verified. It also doesn't check which ports are listening. The Push step rebuilds from cache instead of pushing the exact image that was smoke-tested. There is no SBOM, provenance attestation or signing.

## How versions are pinned and checked
Playwright is pinned in three places: the pyproject dependency (uv.lock 1.56.0), the Dockerfile FROM (tag plus digest) and the CI browser job's `container:` (same digest). The CI check compares `uv export` output with the Dockerfile FROM line using sed. It does not check the ci.yml container pin, and it breaks if two FROM lines match. Renovate groups the `playwright` package with `mcr.microsoft.com/playwright/python`, waits 14 days before taking a release, and pins action digests. KasmVNC is pinned by ARG plus a per-arch sha256 that Renovate does not track (manual bumps). The node image (22.11.0, by digest) and web/.nvmrc (22.11.0) are not cross-checked. uv is pinned to 0.7.8 by digest in the image, but setup-uv in CI has no version (no `[tool.uv] required-version`), so the uv used by CI can drift from the image's. Actions are pinned by SHA.

## Base image: non-numeric USER and a large attack surface
The Dockerfile ends with `USER pwuser` (a name, not a uid). With `runAsNonRoot: true`, the kubelet refuses to start a container whose image user is non-numeric unless the pod sets runAsUser. The upstream Playwright Python noble Dockerfile creates pwuser with plain `adduser pwuser` on ubuntu:noble, which already has `ubuntu` at uid 1000, so pwuser is almost certainly uid 1001 (check with `docker run --rm <image> id pwuser`). Upstream also runs `playwright install --with-deps` with no browser argument, which bakes Chromium, Firefox and WebKit. It installs git, openssh-client, gpg and curl, and runs `chmod -R 777 /ms-playwright` (world-writable browser binaries, harmless only on a read-only rootfs). Our Dockerfile purges curl, but the rest stays in what will be the per-tenant pod.

## Playwright is imported everywhere, which blocks an operator image without Chromium
bcferries/site.py imports playwright.async_api at module level. The modules the operator would keep all import from site.py: server.py (USER_AGENT, SiteBrowser), settings.py (Credentials), views.py (search_url) and watcher.py (Credentials, search_url). pyproject makes playwright a hard dependency. tests/conftest.py autouse-monkeypatches `ferry_watch.server`, `ferry_watch.watcher` and `ferry_watch.views` by dotted path, so every unit test imports Playwright. There is no import-boundary enforcement: ruff's banned-api list is global, not per-module. The fix is to move Credentials, USER_AGENT, BASE_URL and search_url into a Playwright-free module before any split.

## Packaging layout: one wheel, one script, one test tree
Hatch builds a single wheel (packages = ["src/ferry_watch"]) with one console script (`ferry-watch = ferry_watch.__main__:main`). __version__ comes from the `ferry-watch` distribution name. mypy (strict) covers src and tests with mypy_path=src, ruff has src=[src, tests], and pytest has testpaths=[tests]. The image runs `uv sync --locked --no-dev` twice (deps, then the project, non-editable), which installs every dependency. .dockerignore excludes tests, docs and scripts, so the fake BC Ferries site never reaches an image.

## What the single-container runtime expects
Under `tini -g`, entrypoint.sh creates /tmp/.X11-unix. If HOME isn't writable (read-only rootfs) it falls back to /tmp/home. It then starts Xvnc on :99 serving the web viewer and WebSocket on 0.0.0.0:6080 with `-DisableBasicAuth -SecurityTypes None -AlwaysShared`, then matchbox, then `ferry-watch &`, and exits 1 when any one of them exits (`wait -n`). The image serves the KasmVNC web client under /vnc via a symlink and sets BCF_CONFIG=/config/config.json with /config owned by pwuser. terminals.json and alerted.json live next to the config. write_json_atomic calls mkstemp in the target directory, so that directory must be writable. Debug screenshots default to $TMPDIR/ferry-watch. EXPOSE lists 8765 and 6080. The screen size is set twice: SCREEN_WIDTH/HEIGHT for Xvnc (documented) and BCF_WINDOW_SIZE for Chromium (not documented).

## Chromium launch: no sandbox, default /dev/shm, ephemeral contexts
Chromium is launched with only --window-size and --window-position. Playwright's chromium_sandbox defaults to false, so Chromium runs with --no-sandbox. There is no --disable-dev-shm-usage, so pods need an emptyDir (medium: Memory) at /dev/shm instead of the runtime's 64MB default; check whether the external deploy repo already does this. Each session is a fresh new_context with no persistent profile, so cookies live only in memory and the profile in /tmp. Restarting a pod loses the login and the held cart, which belongs to that browser session.
refs: src/ferry_watch/bcferries/site.py:149-160, src/ferry_watch/bcferries/site.py:167-176, README.md:36-38

## Login trusts the configured base URL (matters for e2e and for operator trust)
SiteSession.login navigates to f"{base_url}/login" and fills #email and #j_password without checking that the page is on https://www.bcferries.com. base_url is a SiteBrowser/SiteSession constructor parameter, and the contract tests use it to point at the fake site. A kind e2e against the fake site needs it exposed through an env var. In production, anyone who can set agent pod env (the operator) could then point the login at a host they control and capture BCF_PASS. ROUTE_INFO_URL is a hard-coded constant.

## The fake BC Ferries site can't be reused in a cluster as written
FakeBCFerries is defined inside the test module. The site JavaScript it depends on (passenger counters, fare expansion, cookie banner) is injected by the test's own context.add_init_script, not served by the fake. The queue test relies on Chromium treating *.localhost as loopback, and the browser fixture blocks real hostnames with --host-resolver-rules. Across pods none of that holds. To use it in kind or docker-compose, extract it into a runnable server (`python -m ...`) that inlines SITE_SCRIPT into the HTML it serves, and give it a queue hostname strategy that works across pods.

## Test harness constraints and patterns to reuse
pytest runs with pytest-socket `--allow-hosts=127.0.0.1,::1`, --strict-markers, --strict-config, `filterwarnings=error` and a 60s timeout. Existing tests stand up local aiohttp TestServer fakes for route-info and Pushover. Playwright and the site sit behind Protocols (Session, Browser, TerminalSource) with in-memory fakes in tests/fakes.py. A FakeCluster Protocol or a loopback fake API server for the operator fits these conventions, and an envtest apiserver or kind on 127.0.0.1 passes the socket allow-list. New markers (e.g. apiserver, e2e) must be registered. Deprecation warnings from new Kubernetes/kopf dependencies will fail the suite.

## The operator still needs bcferries.com egress and the web build
Route validation for POST/PATCH trips needs the terminal list, which TerminalDirectory fetches with aiohttp (no browser) from https://www.bcferries.com/route-info. The operator therefore needs egress to bcferries.com unless that lookup moves to an agent. The React build stage and static serving belong only in the operator and standalone images. The KasmVNC web root and symlink belong only in the agent and standalone images.

RISKS:
- The core goal conflicts with the operator's job. An operator allowed to create Pods in a namespace holding tenant Secrets can mount any Secret into a pod of its own and read it. It can also set agent env such as a BCF_BASE_URL that redirects the credential fill at site.py:278-282, or reach VNC through pods/proxy or services/proxy even when NetworkPolicy blocks it directly. Only admission control (VAP with a digest-pinned image, a fixed pod shape and an env allowlist) together with a tight RBAC deny list closes this, and only tests against a real apiserver prove it.
- KasmVNC has no auth and is shared by every viewer (entrypoint.sh:23-24). In multi-tenant, VNC is the path into a logged-in BC Ferries session where users type payment details. If the VNC link in a Pushover alert carries a bearer token, the operator, which sends the alerts, can use it. VNC access must be authorized by the user's identity at the gateway, and NetworkPolicy must deny the operator access to agent port 6080.
- Pods are cattle, carts are not: contexts are ephemeral (site.py:169) and the cart lives in the browser session (README:36-38). Rolling upgrades, node drains, evictions or OOM kills on agent pods lose held carts. Bare pods aren't rescheduled, and a PDB on unmanaged pods only supports an integer minAvailable.
- Per-trip overhead and cold starts: each trip now pays for Xvnc, matchbox, Python and a full Chromium, and a new node must pull a multi-GB Playwright-based image (it includes Firefox and WebKit) before the first check. Scaling out is easier, but the cost per trip is much higher than one shared Chromium with six contexts. GitHub runners may only fit a few agent pods in an e2e run.
- Chromium runs with --no-sandbox (Playwright's default; site.py:154-157), so the container boundary is the only isolation for a compromised renderer. Enabling the sandbox under PSS restricted with RuntimeDefault seccomp generally doesn't work (unprivileged user-namespace clone is blocked). User namespaces for pods (hostUsers: false) depend on the cluster's Kubernetes and containerd versions.
- Test-suite friction: filterwarnings=error (pyproject.toml:84) fails on deprecation warnings from new kopf or kubernetes_asyncio dependencies. Strict mypy has trouble with weakly typed k8s clients. The repo pins aiohttp==3.10.10, which kopf's aiohttp requirement must accept.
- The Playwright pin is checked against only one FROM line (ci.yml:37). With several targets, or a separate agent Dockerfile, the sed check can match zero or two lines and either fail spuriously or stop protecting the agent image.
- NetworkPolicy behavior differs by CNI. kind's default CNI may not enforce policies the way the home cluster does, so netpol e2e can pass in CI and fail at home, or the reverse. Plain NetworkPolicy can't do FQDN egress, so agent egress to only bcferries.com and queue-it can't be expressed without Cilium or Calico extensions.
- ValidatingAdmissionPolicy is GA only from Kubernetes 1.30. On an older home cluster the admission guard needs Kyverno or Gatekeeper instead, which is more to deploy and test.
- The arm64 work is untested today. KasmVNC, Chromium and uv bytecode compilation under QEMU are slow, and nothing has validated that the arm64 image actually runs.

OPEN_QUESTIONS:
- Does the home cluster need arm64 images? CI is amd64-only today, despite the brief.
- Kubernetes version and CNI on the home cluster? This decides VAP (>=1.30), hostUsers:false, NetworkPolicy enforcement and FQDN egress, and which tool the e2e job should use (kind with which CNI, or k3d).
- Does the deploy repo use Flux or Argo, Helm or kustomize? Are you OK with this repo publishing an OCI Helm chart, with CRDs, RBAC, VAP and NetworkPolicies, that the deploy repo consumes with environment-specific values?
- Tenancy unit: one namespace per tenant (cleaner Secret, RBAC and ResourceQuota scoping) or one shared agents namespace? Are tenant namespaces created by GitOps (recommended) or by the operator? The operator would then need namespace-create and RoleBinding powers, which are escalation paths.
- Where do each tenant's BC Ferries credentials live, and how do they reach only that tenant's agent pod: External Secrets or 1Password Connect per-tenant vaults, typed by the user into VNC, or something else? This decides which secret volumes and env the admission policy allows.
- Is the standalone single-container personal mode a supported release artifact going forward, keeping the ghcr.io/mchestr/ferry-watch name, or only a dev path via run-local.sh?
- Operator implementation: Python with kopf (aiohttp-based, matches the stack; no native envtest, so binaries are driven from pytest) or Go controller-runtime (native envtest, but a second language)? This decides whether the operator is a workspace member at all.
- Keep the mcr Playwright base for the agent (digest-pinned, but ships Firefox, WebKit, git, ssh and gpg), or build a slimmer Chromium-only image with `playwright install --with-deps chromium` (smaller attack surface, matches the lockfile automatically, but downloads from Playwright's CDN at build time instead of using a pinned digest)?
- How much e2e to run per PR: kind/k3d on every PR, or only on main, tags and a label? It adds several minutes and needs runner memory.
- Should operator state (trips, settings, alert memory) move from config.json on a PVC to CRDs? That decides whether the operator needs any writable volume and whether it can run more than one replica.
