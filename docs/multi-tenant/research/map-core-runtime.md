===== core-runtime
All runtime state lives in one asyncio process. Nothing is locked, because the HTTP handlers and the Watcher share one event loop. The Watcher holds per-trip browser contexts (_sessions), per-trip check tasks, and three process-wide coordinators: one login lock, one 30-minute login pause after a rejected login, and a Semaphore(3) that caps concurrent checks. Per-trip state sits in TripRuntime: sailings, errors and back-off, the schedule, the alerted set, session info, and the cart state machine (ADDING, READY or FAILED, plus release_requested and expiry). Only config.json (schema v2) and alerted.json are persisted, and alerted.json is written to remember which departures were already alerted and which one was held when the process died. Credentials are read once from BCF_USER/BCF_PASS into a Credentials object. They flow only Settings -> Watcher -> SiteSession.login(), where they are typed into the page; the logged-in state then exists only as Chromium context cookies, which the code never reads or serializes. That makes a per-trip agent pod a natural trust boundary, provided no command returns page content, screenshots or storage state. If each trip gets its own pod, most of the Watcher moves into the agent largely unchanged. Several things are cross-trip today and need cross-pod coordination: login serialization, the login pause (per BC Ferries account), the global enabled switch, the interval, the cart hold time, the single checkout_url, alert-memory persistence, and the activity feed. Pausing a trip must keep its held cart, so pause cannot mean deleting the pod. Any agent pod restart loses the cart, as a process restart does today. The protocol below has 8 commands and about 11 events and covers every control path and state field in the current code. A cheaper alternative also exists: keep the Watcher in the operator and expose the agent's Session protocol over RPC, with a login() that takes no arguments.

## Per-trip session lifecycle: open, walk, reload, back off, re-open
Open: browser.new_session(trip.id) creates a new BrowserContext and page (site.py:167-176), records session_opened_at, then raises held-cart windows because all trips share one X display (watcher.py:308-312, 351-356). Login, when wanted (trip.auto_cart, credentials set, not paused), happens before the search and forces needs_search=True (watcher.py:315-318). Walk: session.search(trip) goes through URL-prefilled route and date, then passengers, vehicle and fare-selection (site.py:303-354). Reload: when needs_search is False, session.refresh() goes to /fare-selection (site.py:356-359). SessionExpired falls back to an in-place search (watcher.py:320-325). On failure, consecutive_errors++ and the back-off is ERROR_BACKOFF_SECONDS=(0,60,120,300,600) by streak. retry_at is set, needs_search=True keeps cookies and login, and after RESET_SESSION_AFTER=3 failures or a closed page the context is closed and re-opened next time (watcher.py:401-417). A 'failing' alert fires exactly once, at the 3rd consecutive failure (watcher.py:421-422). Success clears the error, streak and retry_at (watcher.py:433-438). next_due = now + interval_seconds * U(0.85,1.15) is set in the finally block of every check (watcher.py:264-266). The context is also closed, which drops the login, when: the search key changes (watcher.py:305-307), the trip becomes inactive (disabled, global off, or date past) (watcher.py:207-214, 228-229), a cart add fails (watcher.py:488), a held cart ends (watcher.py:540), the trip is edited mid-cart (watcher.py:463-465), or the trip is removed (watcher.py:190-195).

## Login handling: serialized per process, and one rejection pauses every trip for 30 minutes
_login_lock (asyncio.Lock) allows only one login at a time across all trips (watcher.py:128, 333-338). _login_blocked_until is a single process-wide float: a LoginFailed on any trip sets it to now+LOGIN_BACKOFF_SECONDS (1800) (watcher.py:54, 343-349) and is re-checked inside the lock, so trips queued behind a failure skip their login (watcher.py:335-337). _wants_login also checks it (watcher.py:299-300). The failure is swallowed, so the check continues as a guest (tests/test_watcher.py:292-301, 481-486). Note: auto-cart is gated only on credentials being configured, not on session.logged_in (watcher.py:459). A paused or failed login therefore still produces a guest cart, and BC Ferries refuses a login while a guest cart exists (README.md:124-125; site.py:288-290). The scope is effectively per BC Ferries account, since one account exists per process. The 30-minute figure is also hard-coded in the alert and event wording (notify.py:273; watcher.py:348).

## Check concurrency and timeouts
Each due trip gets its own background task (_start_check, watcher.py:231-240) gated by Semaphore(concurrency=3). Production never overrides the default (watcher.py:113, 127; server.py:512-522). After acquiring a slot the task re-reads config and skips if the trip is gone, edited, holding or inactive (watcher.py:249-255). Timeouts: CHECK_TIMEOUT_SECONDS=900 per check (watcher.py:48, 257-261), CART_BUDGET_SECONDS=40 for fare selection (watcher.py:50, 480), Queue-it wait 10 min (site.py:52, 240-249), action 30s, navigation 60s, results 20s (site.py:49-51). Scheduler: _sleep wakes at the earliest due trip, every CART_POLL_SECONDS=5 while any cart is held, or every IDLE_WAKE_SECONDS=60 (watcher.py:269-291). Held-cart servicing (_service_cart, which calls _empty_cart) and removed-trip cleanup are awaited inline in cycle(), outside any slot or timeout (watcher.py:190-195, 201-204). _empty_cart navigates through _goto and can wait out Queue-it for up to 10 min (site.py:233-249, 400-401). That blocks scheduling of every other trip: a cross-trip coupling that per-pod isolation removes.

## Cart state machine
States: None, ADDING (watcher.py:476), then READY with fare and expires_at = now + cart_hold_minutes*60 (None when 0) (watcher.py:498-499), or FAILED with error, which closes the session (watcher.py:487-489). cart.id is a 12-hex uuid used as an optimistic-concurrency token by release and dismiss (state.py:40; watcher.py:149, 158). holding == READY (state.py:91-93); a holding trip is not checked (watcher.py:201-204, 254). READY exits only in _service_cart, polled every 5s (watcher.py:510-542): (1) release_requested, set by the API: empty_cart if the window is open, event 'Cart released'. (2) Expired with the window open: empty_cart plus a cart_expired alert. (3) Window closed and not lost (the user closed it over VNC): quiet resume, and the departure stays alerted (tests/test_watcher.py:215-224). (4) Lost (page or browser crash): the departure is removed from alerted so it is re-alerted and re-carted, plus a cart_lost alert (watcher.py:529-535). Every exit then sets cart=None and next_due=None (check immediately) and closes the session (watcher.py:537-542). FAILED does not block checking and stays shown until dismissed, a state-only action with no browser work (watcher.py:155-162). Pausing keeps a held cart (tests/test_watcher.py:192). Deleting a trip empties a non-FAILED cart (watcher.py:190-195). A trip edited during fare selection empties and closes (watcher.py:461-468). Process shutdown (_close_all) closes contexts without emptying carts (watcher.py:368-373).

## Checkout-in-progress detection is implicit, and expiry can yank a page mid-payment
The code has no explicit 'checkout in progress' or 'booking completed' signal. While the page is open, not released and not expired, it assumes the user may be checking out. 'Closed' and 'lost' are event-driven: page 'close' marks closed, page 'crash' or Chromium 'disconnected' marks lost, plus page.is_closed() (site.py:162-165, 204-222). This replaced a title poll that misread navigation during payment as a closed window (commit 6016172). When the hold expires and the window is open, the watcher calls empty_cart, which navigates the same page to /abandoned-cart/my-account (watcher.py:520-522; site.py:400-401), even if the user is mid-checkout in VNC. After a successful payment the user closes the window, and watching resumes immediately with next_due=None (watcher.py:539). The trip is not disabled after a booking, so another in-window departure would be carted and alerted.

## Alert memory and dedupe
Dedupe is per trip on departure time: new = available ∧ in_window ∧ not in alerted (watcher.py:441). Departures that sell out again are forgotten, so they re-alert if they reopen (watcher.py:439-440). New departures are added after the alert, whether or not the cart succeeded (watcher.py:470). AlertMemory persists {trip_id: {key, alerted:[HH:MM], held:HH:MM|null}} to alerted.json, skipping writes when unchanged (state.py:128-176). It is saved at the end of every cycle, after an alert, and after a cart exit (watcher.py:221, 471, 542, 586-595). On start, entries are restored only when the stored key matches; the held departure is subtracted so a cart lost in the restart is re-carted, and an event is logged (watcher.py:568-584). The key is repr(trip.search_key()), a Python repr of a tuple holding date and enum objects (watcher.py:96-97; models.py:177-179). It is fragile as a wire or storage key. Activity events (deque of 80, 40 shown) are not persisted (state.py:27, 101; views.py:138).

## Proposed minimal agent<->operator protocol (derived from every control path and state field above)
ENVELOPE (both directions): {v, type, trip_id, agent_boot_id, seq, trip_rev}. trip_rev is an operator-assigned config generation. Every event echoes the rev it was computed under, and the operator drops stale ones. The agent dials out over a WebSocket or gRPC stream, so the operator needs no ingress to the agent. OPERATOR->AGENT: (1) configure {trip: Trip.to_json() (models.py:184-201), trip_rev, active: tenant.enabled && trip.enabled (the date check stays local, watcher.py:229), interval_seconds, cart_hold_minutes, auto_cart_allowed, login_paused_until, alerted: [HH:MM]}. It is idempotent. The agent re-validates with Trip.from_json, resets results and reopens if search_key changed, and closes the session only if not holding. (2) check_now {} clears retry_at and next_due (watcher.py:141-145). (3) release_cart {cart_id} returns an ack or reject (watcher.py:147-153). (4) dismiss_cart {cart_id} (watcher.py:155-162). (5) login_grant {lease_id, ttl}, the reply to login_request, replacing _login_lock. (6) login_pause {until, reason}, a per-account broadcast replacing _login_blocked_until. (7) shutdown {reason: deleted|past|superseded}: empty any non-FAILED cart, close, reply bye (watcher.py:190-195). (8) resync {}, answered with a snapshot. AGENT->OPERATOR: (1) hello {agent_version, protocol v, last_trip_rev, credentials_present: bool, snapshot}. A new boot with a READY cart in the operator's mirror means 'cart lost in restart': drop the held departure from alerted (watcher.py:577-584). (2) heartbeat {ts, loop_heartbeat_at, checking, next_due, retry_at, holding} every 15-30s. (3) check_started {} (watcher.py:387). (4) check_result {checked_at, sailings: [{depart, arrive, vessel, status, note, price, fares:[{name, price, selectable}]}], sold_out_again: [HH:MM], alerted: [HH:MM]} (watcher.py:431-454). (5) opened {new: [Sailing], cart_attempted: bool, cart: Cart|null, alerted: [HH:MM]}, emitted once after the cart attempt (bounded by 40s). The operator renders cart_message or bookable_message from it (watcher.py:458-473, 555-564). (6) check_failed {error (masked in agent), error_at, consecutive_errors, retry_at, session_reset: bool}. The operator sends the failing alert when consecutive_errors == 3 (watcher.py:401-422). (7) session {opened_at|null, logged_in} (watcher.py:311, 318, 363-366). (8) login_request {} and login_result {lease_id, ok, reason (masked)}. On ok=false the operator sets the account pause and broadcasts login_pause (watcher.py:340-349). (9) cart {cart: {id, status, depart, since, fare, price, error, expires_at}|null, transition: adding|ready|failed|released|expired|window_closed|lost|edited|deleted|dismissed, alerted: [HH:MM]}, which mirrors cart_view (views.py:38-50) and the _service_cart branches; the operator sends the expired and lost alerts. (10) activity {kind, text} for the remaining free text ('Opened a booking session', watcher.py:330). (11) bye {cart_emptied: bool}. ## Existing seams make two agent shapes cheap: fat agent vs thin agent
The Watcher depends only on Protocols: Session, Browser, Alerts and TerminalSource (watcher.py:57-85; notify.py:47-50). From the store it uses only .config and .subscribe (watcher.py:131, 186, 251, 265, 426, 461, 573, 590). FAT AGENT: run the existing Watcher in the pod with a one-trip config fed by configure messages. Alerts.submit and RuntimeState.changed() become event emitters, and _slots, _raise_held_windows and the module-wide login lock are replaced by lease and pause messages. The protocol above applies. THIN AGENT: keep the Watcher in the operator, and implement Session as an RPC proxy to the pod (login, search, refresh, add_to_cart, empty_cart, show, close, plus pushed closed/lost flags). The cross-trip coordinators then stay in one process for free. The catch: Session.login takes credentials as an argument (watcher.py:67; site.py:270), so it must become an argless login() that reads the pod's own secret. In the thin shape, carting and alert latency, and any progress at all, depend on the operator being up.

IMPLICATIONS:
- Login coordination must move to the operator as a per-BC-Ferries-account lease (login_request/login_grant) plus a pause broadcast (login_pause). Otherwise each of a tenant's N trip pods logs in concurrently and retries independently after a rejection, which multiplies the account-lockout risk that LOGIN_BACKOFF_SECONDS exists to prevent (watcher.py:54, 128-130, 340-349). The operator only sees ok/fail and a masked reason, never credentials.
- Pause cannot be implemented as pod deletion while a cart is held: today pausing keeps the held cart (watcher.py:201-204; tests/test_watcher.py:192). The operator may delete or scale down an agent pod only when the agent reports holding=false. Otherwise it must send configure{active:false} and keep the pod.
- An agent pod restart equals a lost cart, as process restarts are today (watcher.py:577-584). Rollouts, evictions, node drains and liveness kills of holding pods must be deferred, for example with a PDB or annotation driven by the holding flag. Image upgrades should be rolled per pod when not holding. The upside: operator upgrades no longer touch carts.
- Trip delete must be shutdown, then bye (cart emptied), then pod delete. Also give the agent a SIGTERM/preStop path that empties the cart: today _close_all only closes contexts and leaves the cart sitting in BC Ferries' session until it expires there (watcher.py:368-373).
- checkout_url must become per trip (per pod) in the state view, in each Trip/Cart object, and in cart_message. The frontend schema (web/src/lib/schema.ts:111), WatcherCard (web/src/components/WatcherCard.tsx:222) and CartBanner/App props (web/src/App.tsx:72) change accordingly.
- The operator persists alert memory per trip (replacing alerted.json, state.py:128-176), keyed by trip_id plus trip_rev or a canonical search-key hash rather than repr(search_key()) (watcher.py:96-97). It hands the set back in configure on every agent (re)start, minus a held departure.
- The agent is the trust boundary. Validate every configure with Trip.from_json and existing validators (models.py:203-258). Accept no URL, base_url, file path or script parameters. Never return page HTML, screenshots, cookies or storage_state. Keep debug PNGs pod-local (site.py:407-422). Run describe() in the agent before any error string leaves it (errors.py:40-50).
- Prefer agent-initiated connections (agent dials the operator). The agent pod then needs no ingress except VNC from the authenticating proxy, and the operator never needs to reach into it. Today Xvnc runs with no auth on 0.0.0.0:6080 (entrypoint.sh:87-93), so per-pod NetworkPolicy and per-tenant proxy authorization are what isolate one tenant's VNC from another's.
- The 'login configured' signal must come from the agent (hello.credentials_present) or from Secret metadata, because the operator no longer holds credentials. It drives trip_defaults.auto_cart and the UI (views.py:113, 140) and the auto-cart gate (watcher.py:300, 459).
- The global config splits: enabled and interval become per tenant (or per trip), cart_hold_minutes moves from env to tenant config, and MAX_TRIPS=6 becomes a per-tenant quota (models.py:16, 283-284; settings.py:50). Config schema v3 adds tenant ownership, with a one-time import of the existing config.json and alerted.json. Trip ids are DNS-label-safe (models.py:24) but unique only per config, so pod names should include the tenant.
- Both sides need terminals: the operator for route validation, titles and booking_url (server.py:308-324; watcher.py:546-564), the agent for search_url (site.py:72-87, 306). Have agents fetch the public route-info themselves (terminals.py:23) rather than take operator-supplied labels that feed into navigation.
- Per-pod isolation removes several cross-trip couplings for free: Chromium death taking every cart (site.py:162-165), inline _empty_cart blocking all scheduling for up to the Queue-it timeout (watcher.py:194, 202, 522; site.py:52), shared-display window juggling (watcher.py:351-356), and debug-PNG pruning across trips (site.py:417-418).
- Health splits in two. The agent keeps a local liveness probe (the loop heartbeat, views.py:17), designed so it does not kill a pod that is merely holding a cart. The operator tracks agent staleness from heartbeat messages for the UI and computes next_check_at from the agents' next_due (watcher.py:281).

RISKS:
- Container isolation alone does not meet 'the operator can't get secrets'. Any identity that can create pods in a namespace can mount any Secret there, so an operator with pod-create RBAC can read tenant credentials indirectly unless pod specs are constrained (fixed image and command through an admission policy, no exec or port-forward) or credentials never land in a namespace Secret the operator can reference.
- If tenants enter BC Ferries credentials through the operator's dashboard and API (the natural UX), the operator sees them in transit, which violates the requirement. The intake path needs a deliberate design.
- Fixed per-trip overhead: each pod runs its own Xvnc, matchbox, Chromium and Python runtime (entrypoint.sh:87-103), replacing one shared Chromium with N contexts (site.py:167-176). Not measured here. Scaling is linear in trips, not users.
- Many pods polling BC Ferries from the same cluster egress IP at intervals as low as 15s (models.py:19) could trigger Queue-it or rate-limiting site-wide. The only throttle today, Semaphore(3) (watcher.py:127), disappears per pod.
- Held carts become vulnerable to ordinary Kubernetes disruption (evictions, node drains, OOM kills, liveness restarts, image rollouts). Today only a whole-service restart loses them.
- Under the fat-agent design an operator outage leaves carting working but stops alerts, because Pushover and wording live in the operator. A user may not learn a cart is held before cart_hold_minutes expires and the cart is emptied (watcher.py:520-528).
- Hold expiry empties the cart by navigating the same page the user may be paying on over VNC (watcher.py:520-522; site.py:400-401). With more tenants and remote checkout this becomes more likely. There is also no booking-completed detection, so a trip can cart again right after a successful checkout (watcher.py:539).
- Auto-cart proceeds as a guest when login failed or is paused (watcher.py:459 ignores session.logged_in), and BC Ferries refuses login while a guest cart exists (README.md:124-125). The tenant then has to pay as a guest over VNC, typing card data into the pod.
- Error strings crossing to the operator are masked only for username and password (watcher.py:122; errors.py:46-49). LoginFailed carries BC Ferries' on-page alert text (site.py:295-300), which is low risk but is page content leaving the pod.
- Ordering and race hazards move from one event loop to a network hop. An edit during a check or fare selection is handled today by in-process re-reads (watcher.py:251-255, 426-428, 461-468). Without trip_rev on every message, stale results or carts could be applied to an edited trip.

OPEN_QUESTIONS:
- Is the login-coordination key one BC Ferries account per tenant, or can a tenant have several accounts, or can tenants share one? This decides the scope of the login lease and the 30-minute pause.
- How should a tenant's BC Ferries credentials reach their pods without passing through the operator? Options: a tenant-owned Secret created out of band (e.g. 1Password/External Secrets, as run-local.sh hints with op://kubernetes/ferry-watch); a client-side-encrypted blob the operator only relays; or no stored password at all, with the tenant logging in once via VNC, which requires keeping the login across session resets.
- Fat agent (Watcher per pod, typed events, agent autonomous if the operator is down) or thin agent (operator keeps the Watcher and drives a Session RPC with an argless login(); smaller change, operator in the loop)?
- Should alerting stay in the operator, which then holds the Pushover app token and per-user keys, or move partly into agents? Is a tenant's Pushover user key considered a secret the operator must not hold?
- Pod lifecycle for paused, disabled or past trips that hold no cart: keep the pod warm (cost, and the login stays) or delete it and recreate on resume (cold start, fresh login and Queue-it)?
- Are enabled, interval and cart_hold per tenant or per trip, and what quotas replace MAX_TRIPS=6? Is a global check budget toward BC Ferries across all tenants needed?
- Which disruptions may kill a held cart? Should agent image rollouts wait for carts to clear, and should the liveness probe be suppressed while holding?
- Should a completed checkout be detected (for example a confirmation URL) to stop the trip or suppress hold-expiry navigation, instead of relying on the user closing the window?
- Should tenants be able to see their own failure screenshots (served from their pod behind the VNC auth), given they must never be shipped to the operator?
- Where does operator-side persistent state live: CRD spec and status, a database, or a ConfigMap? This covers trips, per-trip alerted sets and trip_rev, and a migration for the existing config.json and alerted.json is needed.
