===== threat-model
Today Ferry Watch is a single trust domain. One process holds BCF_USER/BCF_PASS from env. One Chromium runs a browser context per trip, and all of them sit on a single unauthenticated KasmVNC display. The API and WebSocket have no notion of identity, so per-tenant isolation needs new identity plumbing as well as per-pod browsers. The target design holds up only if three things are true. (1) The automation runs inside the browser pod behind a narrow, declarative command API, with no CDP or Playwright port exposed. A remote CDP connection gives whoever holds it every cookie and the password. (2) The internet-facing component cannot shape browser pods. In Kubernetes, permission to create pods in a namespace effectively means reading every Secret and using every ServiceAccount in it, through image, command, env (e.g. DEBUG=pw:protocol, SSLKEYLOGFILE), exec probes, lifecycle hooks, ephemeral containers or an image patch. So the "operator" should be split into an internet-facing API with no pod or secret rights and a no-ingress reconciler that stamps pods from a fixed template, enforced by a ValidatingAdmissionPolicy. (3) VNC never passes through the operator and never shares its origin. Today the viewer is deliberately on the app's hostname, so a compromised dashboard's JS could drive the VNC using the user's own Authelia cookie. A separate gateway on per-tenant subdomains, bound by Authelia's domain_regex User group, plus NetworkPolicy and an in-pod auth shim, closes this. For credential intake, B (the user logs in inside the headed browser over VNC) is the only option where nothing except the browser pod ever sees the password. C (agent-served form via the gateway) and D (Vault bound to the pod identity) tie for second. A (dashboard form) fails because the operator handles the plaintext. One catch for B: BC Ferries keeps the search and cart in a server-side session, so one login's cookies cannot be cloned across per-trip pods. Residual risks no design removes: a compromised operator still serves the dashboard and composes alerts, so it can phish; any VNC session can take over the account and use saved cards; and Playwright launches Chromium without its sandbox by default, so the container is the only barrier against a renderer exploit. The cluster admin (the owner) is out of scope and must be explicitly trusted by tenants.

## Today's trust model is single-tenant end to end (why per-pod isolation is needed, and why it is not enough on its own)
Credentials come from env (BCF_USER/BCF_PASS) and the Watcher uses them for every trip. SiteBrowser owns ONE Chromium; each trip is a BrowserContext in it. Every context renders on one X display (:99), which Xvnc serves with -DisableBasicAuth -SecurityTypes None, bound to 0.0.0.0 with -AlwaysShared. The watcher also raises held-cart windows to the front for the viewer. So any VNC viewer can switch to any trip's logged-in window, and tenants cannot share this browser. The API has no identity at all; it relies on Authelia in front. The WebSocket hub sends ONE global snapshot to every client, and that snapshot contains all trips, events and checkout_url. Mutations are guarded only against cross-site requests (CSRF), and requests with no Origin or Sec-Fetch-Site header count as same-origin. Multi-tenancy therefore needs tenant identity in the API and a per-tenant fan-out, not just per-tenant pods.

## How login, carts and checkout work, and what that means for the assets
Login exists only so saved payment cards are available at checkout. The watcher logs in BEFORE searching, because BC Ferries' login form will not accept a login while a guest cart exists. The search and the cart live in a server-side session tied to the browser's cookies, and checkout happens in that same browser over VNC; the cart alert links to checkout_url. `logged_in` is a one-way flag set after login, and nothing detects a later logout or expiry. Consequences: (a) whoever holds the session cookies or the VNC view can check out with the tenant's saved cards, see PII and booking history, and reach account settings to change the email or password (account takeover). So the VNC session is close to password-equivalent. (b) Session cookies cannot be copied between per-trip pods: they would share, and clobber, one server-side search and cart. (c) A VNC-login model (option B) needs new 'still logged in?' detection, plus a policy for auto-cart when the session lapses, because a guest cart then blocks re-login.

## Secret hygiene already in the code, which the in-pod agent should keep
Credentials.password is repr=False. login() drops every Playwright error with `from None`, because Playwright call logs echo fill() values. describe() keeps only the first line of an error and masks known secrets. Pushover errors redact the token and user key. Screenshots are viewport-only and are kept out of the backed-up config volume. aiohttp access logs are off. Gaps that matter once output crosses a trust boundary: (1) LoginFailed embeds text taken from the page's alert element, and that text goes into events and a Pushover alert. (2) describe() keeps the first exception line, which can contain URLs, for example Queue-it tokens or a ;jsessionid path parameter. (3) log.exception writes full tracebacks in several places. (4) Under option A, C or D the password sits in agent memory, and env vars are visible in /proc/1/environ and in crash dumps; files on tmpfs are better than env.

## Remote CDP / Playwright connect from the operator gives it full secret access; run the agent in the pod
If the operator drives Chromium remotely (connect_over_cdp or a Playwright run-server), it must hold the password to type it (site.py:281-282). It also gets context.cookies() and storage_state(), page.evaluate, network interception (Cookie headers), screenshots of account pages, and call logs containing fill() values. No RBAC rule or NetworkPolicy can shrink that: the channel itself is the secret. Today's launch passes only window arguments and uses Playwright's default pipe transport, with no --remote-debugging-port. Keep it that way. The current watcher.py and site.py become the agent inside the browser pod, and nothing listens except the agent API and VNC; check this in CI with `ss -ltnp` inside the container. Xvnc runs without X authorization, so any process in the pod can inject input or read the screen through X. The pod is therefore the trust boundary: no sidecars, no shared /tmp/.X11-unix, no ephemeral containers.

## Being able to create pods means being able to read secrets unless the pod spec is pinned (operator creating pods)
Kubernetes' RBAC good-practices guide warns that anyone who can create workloads in a namespace can mount any Secret and run as any ServiceAccount in that namespace. Concrete ways a compromised operator with pods/create in a tenant namespace can get secrets out, even with no secrets verbs: (1) Its own image, or a command/args override such as `sh -c 'cat /creds/*'`. (2) Env vars that change what the PINNED image does: DEBUG=pw:protocol makes the Playwright driver print protocol traffic to stderr, which can include the typed password and response headers; SSLKEYLOGFILE plus HTTPS_PROXY lets an attacker's proxy decrypt the browser's TLS; BCF_DEBUG_DIR (settings.py:56) can send screenshots to a shared volume; LD_PRELOAD or PYTHONPATH load attacker code; credentials set as literal `value:` env entries are readable by anyone with `get pods`. (3) envFrom or secretKeyRef, or a volume mounting the victim's Secret or PVC. (4) Exec liveness/readiness probes and postStart/preStop hooks run commands in the pinned image, and failing-probe output is recorded in Events. (5) Extra containers, initContainers, or shareProcessNamespace (read /proc/<pid>/environ and memory). (6) pods/ephemeralcontainers, i.e. kubectl debug with targetContainerName. (7) Patching a running pod's container image (the image field is mutable), which restarts it with attacker code while keeping its volumes. (8) serviceAccountName set to the browser SA, or serviceaccounts/token create, to impersonate the pod to Vault (option D). Controls: the internet-facing API gets NO pod verbs. A separate reconciler with no ingress stamps pods from a hard-coded template. A ValidatingAdmissionPolicy (GA in Kubernetes 1.30) or Kyverno, scoped to tenant namespaces, enforces: a single container image pinned by digest; no command/args; an exact env list; no envFrom; only allow-listed volumes (memory-backed emptyDir plus that tenant's own PVC); only httpGet/tcpSocket probes; no lifecycle hooks; no init or ephemeral containers; shareProcessNamespace false; automountServiceAccountToken false; fixed serviceAccountName and runtimeClassName; and it rejects UPDATE of the pod spec. The tenant namespaces also run PSA `restricted`. With one namespace per tenant, even a valid pod can mount only its own tenant's objects.

## RBAC: what each control-plane component may and may not hold
API/dashboard pod: no verbs on secrets, pods or any pods subresource. It only writes trip custom resources, or calls the reconciler. Reconciler: create/delete/get/list/watch on pods and services in tenant namespaces, and nothing else. Forbidden for both: (1) secrets get/list/watch, because list and watch return the data. (2) secrets patch, because a patch response returns the whole object including existing data, so 'update-only' RBAC that includes patch leaks the secret; server-side apply is a patch. (3) pods/exec, pods/attach. (4) pods/portforward, which reaches VNC on :6080 and the agent port directly and bypasses the gateway. (5) pods/log. (6) pods/ephemeralcontainers. (7) pods patch/update, which allows an image swap or relabelling a pod into NetworkPolicy groups. (8) serviceaccounts/token create. (9) nodes/proxy, which allows exec through the kubelet. (10) roles/rolebindings with bind or escalate, or binding the admin/edit ClusterRoles, which include secret read and exec. (11) networkpolicies: policies are additive, so one extra allow opens :6080. (12) services, ingresses or httproutes in tenant namespaces outside the template. (13) Configmaps that the browser pod or gateway trust. (14) ValidatingAdmissionPolicy objects, webhooks and CRDs, which would let it disable the guardrails. (15) events in tenant namespaces, which carry probe output. (16) Wildcards such as pods/* or *. The only Secret verb that is ever acceptable is bare `create` (option A), and that still does not help against a live compromise.
refs: https://kubernetes.io/docs/reference/access-authn-authz/rbac/#privilege-escalation-prevention-and-bootstrapping

## VNC must not pass through, be authorised by, or share an origin with the operator
Proxying: an operator in the VNC path sees every frame and every keystroke. Frames include account PII, the cart and masked cards. Keystrokes include the BC Ferries password under option B and any card number or CVV typed at checkout. It can also inject input: open DevTools and read cookies, change the account email or password, or check out with saved cards. TLS does not help, because the operator would also serve the viewer's JS. Having the operator only make the authorisation decision is not enough either, because a compromised operator would authorise itself. Same origin: the Dockerfile deliberately serves KasmVNC's viewer under /vnc on the app's hostname. Once the dashboard origin is compromised, its JS can open a WebSocket to the VNC path carrying the user's own Authelia cookie and drive that tenant's browser, with no network path from the operator needed. Controls: (1) Put VNC on its own origin, one per tenant, e.g. <tenant>.vnc.example. Authelia's `domain_regex` with the named `User` group makes the IdP itself require that the user matches the subdomain's tenant. The tenant always comes from the authenticated host name, never from a path or query parameter. (2) The gateway (Authelia forward-auth plus nginx or Envoy) is configured statically and sits outside operator RBAC. It routes /<trip>/ to browser-<trip>.ferry-<tenant>.svc:6080, with names checked against ^[a-z0-9]{1,32}$. (3) Authorise both vnc.html and the WebSocket upgrade, and block KasmVNC's /api/ endpoints. Check Origin on the upgrade, set frame-ancestors 'none', and use host-only cookies. (4) NetworkPolicy: only gateway pods reach :6080. (5) Inside the pod, bind Xvnc to 127.0.0.1 (today it binds 0.0.0.0) behind an in-pod auth shim. The shim checks a short-lived token signed by the gateway, with audience <tenant>/<trip> and the gateway's public key baked into the image. Alternatively use per-pod KasmVNC basic auth. Either way a NetworkPolicy gap alone does not open VNC. Also drop -AlwaysShared so a hidden second viewer cannot watch. Alert links carry no bearer token; anything in a link leaks through Pushover, notification history and browser history.

## KasmVNC attack surface to verify before relying on it
-DisableBasicAuth -SecurityTypes None means there is no credential at all. KasmVNC also has a developer HTTP API on the same port that needs owner credentials, covering screenshots and runtime permission changes. What that API allows with basic auth disabled needs testing; block /api at the gateway regardless. Confirm with `ss -ltnp` that no legacy RFB TCP port (5900+N) and no X11 TCP port is listening. Confirm that UDP/WebRTC streaming stays off (`-publicIP 127.0.0.1` keeps it from looking up a public IP). Keep -Log at a low level, since verbose input logging could record keystrokes. KasmVNC's clipboard lets a VNC user copy out anything they can see, including cookie values from DevTools. That is fine for the tenant and decisive for an intruder. A Chromium managed policy of DeveloperToolsAvailability=2 narrows it; check that Playwright's pipe still works with it.

## Chromium runs without its own sandbox, so the container is the only barrier (compromised browser pod)
site.py does not set chromium_sandbox, and Playwright's documented default is false (it adds --no-sandbox). That is common in containers because the default seccomp profile blocks user namespaces. A renderer exploit from any page the browser loads therefore runs as pwuser in the pod. Those pages include bcferries.com's third-party scripts, Queue-it, payment/3DS frames, and anything a tenant browses to over VNC. From there it has the agent's memory and env (the password under A, C or D; BCF_PASS today), the profile's cookies, keystrokes on the X display, and the pod's network. Controls: (1) Turn on chromium_sandbox with a Localhost seccomp profile that allows CLONE_NEWUSER, after checking the host's AppArmor restriction on unprivileged user namespaces; or run browser pods under gVisor or Kata via runtimeClassName. (2) No ServiceAccount token, read-only root filesystem, all capabilities dropped, HOME on tmpfs (entrypoint.sh already supports a read-only root). (3) Deny egress to RFC1918, 100.64/10, 169.254/16, node IPs and the API server, so the pod cannot reach the home LAN, the kubelet or other pods. (4) A Chromium managed-policy URLAllowlist covering bcferries.com, queue-it.net and the payment/3DS hosts checkout needs (to be measured), with PasswordManagerEnabled=false and AutofillCreditCardEnabled=false.

## Agent command API: declarative, so no command can be used to exfiltrate
Inbound commands (operator to agent) use mTLS or a bearer token issued by the reconciler, and NetworkPolicy admits only the API/reconciler pods. The whole command set: (a) PUT /v1/watch: a Trip in today's JSON shape, validated BY THE AGENT with Trip.from_json. That already rejects unknown fields, accepts terminal codes only as ^[A-Z]{3}$ and ids only as ^[a-z0-9]{1,32}$, bounds passengers, height and times, and keeps the interval within 15-3600 s. (b) POST /v1/check-now, rate-limited in the agent. (c) POST /v1/cart/release {cart_id} and POST /v1/cart/dismiss {cart_id}; release only ever goes to the fixed /abandoned-cart URL. (d) GET /v1/status. There are deliberately NO commands for: URL, selector, JS/evaluate, init script, headers, user agent, proxy, Chromium flags, base_url (SiteBrowser and SiteSession accept one, and it must stay unreachable from config), log level, tracing/HAR/video, fetching screenshots, cookies or storage state, credentials, upload/download, or checkout. The agent builds every URL itself from the constant BASE_URL via urlencode, and fetches the terminal list itself from bcferries.com, never from the operator. Outbound status is typed and bounded: sailings (times, status enum, price matching a money pattern, vessel at most 64 characters), cart {id, status enum, depart, fare enum, price, expires_at}, session {opened_at, logged_in, needs_login}, and errors as ENUM codes. No free text from the page or from exceptions crosses the boundary. The agent also owns the abuse limits the operator must not be able to reset. The 30-minute login backoff lives only in memory today, so a compromised operator could restart pods to retry logins and lock the tenant's account. Persist it on tenant storage, and cap carts per hour.

## Which way reports flow back, and lateral movement from a compromised browser pod
Prefer pull: the API or reconciler polls GET /v1/status, or holds a stream it opened itself. Then browser pods have no network route to the control plane at all. If you push instead, the operator's ingest endpoint must authenticate each agent and bind each report to that pod's tenant and trip. Use a projected SA token with an operator-only audience checked via TokenReview, or per-pod mTLS. Otherwise a compromised pod A can post status or 'cart ready' events for tenant B. Either way, treat agent output as untrusted: validate the schema, cap lengths, and render it as text. React escapes by default, and web/src has no dangerouslySetInnerHTML. Never put an agent-supplied URL into an alert; the VNC link is built from the operator's own template, as checkout_url is today.

## Credential intake ranked against 'a compromised operator cannot get the secret'
1st, B (log in to BC Ferries inside the headed browser over VNC through the gateway; the agent keeps only cookies). The password goes from the user through the gateway to the pod as RFB keystrokes and is never stored. The operator never sees it, provided VNC does not pass through the operator and the origins are separate. Residual risks: (a) The cookies live on the pod's tmpfs or a tenant PVC. Anything that can create a pod mounting that PVC can read them, so the pinned pod spec still matters. Backups. (b) Expiry needs a re-login over VNC, and because of the server-side session, each per-trip pod needs its own login unless BC Ferries issues a separate long-lived 'remember me' cookie. (c) Users are trained to type their password into a remote viewer rather than bcferries.com, and password-manager domain binding cannot help, so a compromised operator can phish with a fake viewer. (d) A compromised Chromium sees the keystrokes during login. 2nd (tie), C (an agent-served credential page reached only through the gateway origin). The operator never sees the password, the agent can log in unattended, and per-trip pods are easy. Residual: the password is stored in tenant storage or memory, so a browser-pod compromise reveals a reusable password; plus the same phishing and pod-spec issues. Keep it in memory only (re-prompt after restart), or in a tenant-scoped volume excluded from backups. 2nd (tie), D (Vault, 1Password Connect or External Secrets bound to the browser pod's identity). This is only as good as (i) an intake path that bypasses the operator, e.g. users writing to Vault directly through OIDC under a templated per-user policy, and (ii) pod creation being pinned. Without (ii), the operator creates a pod with the browser SA and logs in to Vault as it. Ingesting via External Secrets turns the secret back into a k8s Secret, and the ESO controller can read every one. It adds audit and rotation but is heavy infrastructure for a home cluster. 4th, A (the user types credentials into the dashboard; the operator writes a Secret with create/update-only RBAC). It fails: the operator process handles the plaintext and serves the JS that collects it, so anything entered after a compromise is captured. Encrypting in the browser to the pod's public key does not fix that, because the operator serves both the JS and the key. RBAC protects only Secrets written BEFORE the compromise, and only if it excludes patch (returns the data), list/watch, and pod creation that could mount the Secret. Recommendation: B by default, with C (in memory) as an opt-in for unattended re-login.

## Logs, screenshots and other artefacts
Today: viewport screenshots are taken on MarkupChanged and unexpected errors and on cart failures (on cart and fare-review pages they can show names and fares). They go to BCF_DEBUG_DIR, $TMPDIR by default. Full tracebacks are logged with log.exception. KasmVNC logs to stderr. Chromium's profile and crash reports live under HOME=/tmp/home. Rules for multi-tenant: (1) Screenshots stay on the pod's tmpfs and there is NO endpoint to fetch them; a 'support screenshot' feature would be an exfiltration channel. (2) Never enable Playwright tracing, HAR or video (none today), and keep DEBUG/PWDEBUG out via admission. (3) Turn off Chromium crash dumps and core dumps (RLIMIT_CORE=0). (4) Set PasswordManagerEnabled=false and AutofillCreditCardEnabled=false; on Linux with no keyring, Chromium's saved passwords and cards are effectively plaintext on the profile volume. (5) Deny pods/log to the API pod, and keep the API out of the cluster log store, which collects tenant pods' stdout from every node. (6) Errors leave the pod only as enums.

## Tenant-vs-tenant isolation
(1) API IDOR: trip ids are 8 hex characters and cart ids 12, and routes look trips up by id only. Every lookup must be scoped to the tenant taken from the authenticated identity: Authelia's Remote-User header, trusted only because NetworkPolicy lets only the proxy reach the API. The Hub must send each tenant its own snapshot. (2) VNC IDOR: never take the tenant from the URL, and authorise the WebSocket upgrade, not just vnc.html. Otherwise guessing an 8-hex trip id opens someone else's viewer. (3) Namespace per tenant beats one namespace with labels. Per-namespace scoping of Secrets, PVCs and ServiceAccounts, PSA, a ResourceQuota (pods up to MAX_TRIPS=6, memory) and default-deny NetworkPolicy come for free. In a single namespace, every tenant's Secret can be mounted by any pod the reconciler creates, and isolation rests on one admission rule comparing labels set by the very component it is checking. (4) NetworkPolicy: default-deny ingress and egress in each tenant namespace. Ingress to :6080 only from gateway pods, and to the agent port only from API/reconciler pods. Peers must AND a namespaceSelector on the immutable kubernetes.io/metadata.name label with a podSelector; a podSelector alone, or a namespaceSelector on a mutable label, can be satisfied by a pod or namespace the operator creates. Egress: DNS, plus 80/443 to 0.0.0.0/0 except RFC1918, 100.64/10, 169.254/16 and the node CIDR. How the API server and host-network endpoints are handled depends on the CNI, so test from a browser pod. Browser pods never talk to each other. (5) Per-pod VNC credentials: see the VNC finding. (6) Abuse: a tenant's VNC browser is a general-purpose browser on the owner's home IP, which carries legal exposure; use URLAllowlist and egress limits. All tenants share one egress IP, so one tenant's aggressive polling or failed logins can get it blocked by BC Ferries or Queue-it for everyone.

## Pushover keys and alert content let a compromised operator phish
Today the operator holds the Pushover app token and the user key, and writes every alert's title, body and URL. A compromised operator with every tenant's user key can send convincing high-priority alerts such as 'session expired, tap to log in' that link anywhere, phishing for BC Ferries passwords. This is worse under option B, where users already type their password into a remote viewer. It also serves the dashboard, so it can show a fake login form there. Mitigations: alerts link only to the tenant's VNC origin, and users are told that is the only place to log in. Optionally the agent sends its own alerts: it holds the tenant's user key (entered through the gateway path) and the shared app token, so the operator never has user keys. The cost is that every pod then holds the app token, which only allows quota abuse because sending also needs a user key.

## Cluster admin and backups are out of scope, and that should be stated
Whoever administers the cluster can read Secrets and etcd, exec into pods, read PVs, edit admission policies and NetworkPolicies, and reach any VNC session. Nothing in this design defends against them, so tenants must be told the owner can technically access their BC Ferries session. Backups extend that exposure: the code already treats /config as backed up. Tenant cookie or credential volumes must be excluded from Velero, VolSync or Longhorn backups, or encrypted, or those secrets live on in backup storage. CI pushes the image unsigned. A digest pin in admission is enough on its own, and cosign signing plus verification is optional hardening against registry tampering.

IMPLICATIONS:
- Split the 'operator' into two Deployments: ferry-api, which is internet-facing behind Authelia, serves the dashboard and has NO verbs on pods, secrets or their subresources; and ferry-reconciler, which has no ingress Service and a pinned image, and turns per-trip CRs into pods/services in tenant namespaces from a hard-coded template. Threat (1), the compromised internet-facing pod, then lands on a component that cannot shape pods.
- Use one namespace per tenant, created at onboarding with an immutable owner label: PSA enforce=restricted, a default-deny ingress+egress NetworkPolicy, a ResourceQuota (pods up to MAX_TRIPS=6, memory and CPU), and a LimitRange. Give the reconciler a ClusterRole bound into each tenant namespace through RoleBindings created by onboarding, not by the reconciler.
- Write a ValidatingAdmissionPolicy (needs k8s 1.30+) or Kyverno policy for tenant namespaces that rejects every pod not matching the template exactly. That means: image digest; no command/args; an exact env list (in particular no DEBUG, PWDEBUG, SSLKEYLOGFILE, *_PROXY, LD_PRELOAD, PYTHON*, BCF_DEBUG_DIR); no envFrom; volumes limited to memory-backed emptyDir plus that tenant's own PVC; httpGet/tcpSocket probes only; no lifecycle hooks, initContainers or ephemeralContainers; shareProcessNamespace false; automountServiceAccountToken false; fixed serviceAccountName and runtimeClassName. Also deny pod UPDATE and pods/ephemeralcontainers for everyone except cluster admins.
- Browser pod image: Xvnc bound to 127.0.0.1 (not 0.0.0.0 as in entrypoint.sh:22), without -AlwaysShared, fronted by an in-pod auth shim on :6080 that checks a short-lived gateway-signed token (public key baked into the image). Playwright on its default pipe, with no debugging port. The agent API on a separate port. chromium_sandbox=True with a Localhost seccomp profile, or gVisor. Chromium managed policies: URLAllowlist, PasswordManagerEnabled=false, AutofillCreditCardEnabled=false, DeveloperToolsAvailability=2 if Playwright tolerates it. Read-only root filesystem and tmpfs /tmp and HOME.
- The VNC gateway lives in its own namespace on its own wildcard origin *.vnc.<domain>. An Authelia access_control rule with domain_regex '^(?P<User>[a-z0-9]+)\.vnc\.<domain>$' binds tenant to user. Its routing is static and regex-validated (browser-<trip>.ferry-<tenant>.svc:6080), it authorises the WebSocket upgrade and checks Origin, blocks /api/*, and sets frame-ancestors 'none'. The gateway's config is not writable by the API or the reconciler.
- NetworkPolicy peers always AND namespaceSelector{kubernetes.io/metadata.name} with a podSelector. Browser pods accept :6080 only from the gateway and the agent port only from the API/reconciler. Egress is DNS plus 80/443 to 0.0.0.0/0, except 10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16, the node CIDR and the API server. Verify with an in-pod curl matrix because API-server handling depends on the CNI. The API accepts ingress only from the ingress controller, which is what makes Remote-User trustworthy.
- Refactor the code: Watcher and SiteSession become a single-trip in-pod agent behind PUT /v1/watch, POST /v1/check-now, POST /v1/cart/{release,dismiss} and GET /v1/status, validated in the agent with Trip.from_json. Errors leave the pod as enums. Login backoff and cart-rate limits persist on tenant storage. The agent fetches terminals itself. Remove the BCF_USER/BCF_PASS env path for multi-tenant mode.
- Make the API multi-tenant: derive the tenant from the trusted Remote-User header on every request, scope every store, state and trip/cart lookup by tenant, and make Hub fan-out per tenant (server.py:145-161 is global today). Alert URLs are built from the operator's own template, not from agent data, and carry no bearer token.
- Credential intake defaults to B: login over VNC. The agent detects a logged-out session, sets needs_login, and alerts with a link to the tenant's VNC origin. Cookies are persisted either to a memory-backed emptyDir (re-login after every pod restart) or to a per-trip PVC excluded from backups. An optional C mode serves an agent credential page through the gateway and keeps the password in memory only.
- Isolation is per tenant, not per trip. Per-trip pods multiply login sessions and BC Ferries' view of concurrent account activity, and under B they multiply VNC logins too. Decide pod granularity on that basis, not for security.
- CI: assert inside the image that only the agent port and 6080 listen (ss -ltnp), that Chromium is launched with the sandbox (no --no-sandbox), and that no tracing or screenshot-export code path exists. Optionally sign images with cosign and verify them in admission.

RISKS:
- 1. Phishing by a compromised operator, high likelihood and high impact. It still serves the dashboard origin and (unless the agent sends alerts) holds every Pushover user key and writes alert URLs. It can show fake login forms or fake 'log in again' viewers and harvest BC Ferries passwords. Separate origins and user education reduce this but do not remove it. Option B makes it worse, because users learn to type the password somewhere other than bcferries.com.
- 2. Gaps in the pod-spec guardrails, high likelihood that something is missed. If the API/reconciler split or the admission policy is skipped or incomplete, a compromised operator reads every tenant's secrets. Typical misses: one env var (DEBUG=pw:protocol, SSLKEYLOGFILE), an exec probe or lifecycle hook, a mutable image tag, ephemeral containers, or patching a pod's image.
- 3. A shared or reachable VNC origin. If the dashboard and VNC share an origin or cookie scope, or the gateway does not authorise the WebSocket upgrade and check Origin, a compromised dashboard drives each user's own VNC session with their IdP cookie. That means cookie theft through DevTools, account takeover, and checkout with saved cards.
- 4. Holding a VNC session means holding the BC Ferries account: change the email or password, see PII, check out with saved cards. A gateway compromise therefore exposes every tenant at once, making the gateway the new crown jewel; keep it off-the-shelf with a static config.
- 5. A compromised browser pod. Chromium runs without its sandbox by default, so one renderer exploit yields that tenant's cookies, any stored password (C/D/A) and VNC keystrokes. If egress is not restricted, it can also pivot to the home LAN, the kubelet or the API server. CNI quirks can silently fail to block the API server.
- 6. NetworkPolicy mistakes. Policies are additive, peers matched only by label can be spoofed by pods the operator creates, and enforcement depends on the CNI. Any of these can expose :6080 or the agent port. The in-pod auth shim is the backstop.
- 7. Artefact leakage. Screenshots, crash dumps, verbose KasmVNC logs, Chromium's effectively plaintext saved-password/card store, and the cluster log store each carry secrets out of the pod unless every one is disabled or confined.
- 8. Integrity and availability attacks by a compromised operator. It can release carts, disable trips, or restart pods to reset in-memory login backoff and lock tenants' BC Ferries accounts. It cannot complete checkout as long as no checkout command exists.
- 9. Cross-tenant availability. All tenants share one egress IP, so one tenant's polling or failed logins can get it blocked by BC Ferries or Queue-it for everyone. A malicious tenant can also use the browser for general browsing from the owner's home IP.
- 10. Persisted session state, plus a stored password under C/D, sitting in PVCs and backups beyond the pod's lifetime.
- 11. The cluster admin (the owner) and the backup infrastructure can access everything. This is out of scope, and tenants must be told.

OPEN_QUESTIONS:
- Does BC Ferries issue a long-lived 'remember me' cookie, separate from the session that holds the search and cart, and how long do logged-in sessions last? This decides whether option B needs a VNC login per trip pod and how often users must re-login.
- Intake policy: B only (no stored password, re-login over VNC on expiry or restart), or B plus an opt-in C/D mode that stores the password for unattended re-login, accepting that a browser-pod compromise then reveals a reusable password?
- Session persistence: memory-backed emptyDir (re-login after every deploy or pod restart), or a per-trip PVC (survives restarts, wider exposure, must be excluded from backups)?
- Are you willing to split the 'operator' into an internet-facing API with no pod or secret rights and a no-ingress reconciler? The security case for 'the operator cannot get secrets' depends on it.
- Who sends Pushover alerts? The operator (simpler, but it holds every user key and can phish), or each agent (the operator never sees user keys; every pod holds the shared app token)?
- Cluster facts: Kubernetes version (ValidatingAdmissionPolicy needs 1.30+, or will you run Kyverno?), CNI (Cilium/Calico/flannel decides FQDN egress and API-server blocking), whether gVisor or Kata is available, and the node OS's AppArmor user-namespace restriction (for the Chromium sandbox).
- Who are the tenants: family and friends, or strangers? This sets how much to invest in tenant-vs-tenant hardening, in URL allowlisting against misuse of your home IP, and in telling tenants that you, as cluster admin, can technically access their sessions.
- Is one pod per trip required, or is one pod per tenant (with a context per trip) acceptable? Isolation is per tenant either way; per-trip pods multiply logins and concurrent sessions on the account.
- Can saved cards be charged at BC Ferries checkout without re-entering the CVV? This sets the impact of a stolen session or VNC session.
- Can you run a wildcard DNS name and TLS certificate (*.vnc.<domain>) for per-tenant VNC origins, and are the Authelia access-control rules managed outside anything the app can write?
